

### 수직 분할

* **배경:** 상품 서비스에서 '상품 기본 정보(상품명, 가격)'와 '통계 정보(조회수, 판매량)'를 관리하는 방식을 설계함.
* **문제:** 
	* **생명주기 불일치:** 기본 정보는 주로 SELECT되고 거의 변하지 않는 반면, 조회수는 클릭 시마다 실시간으로 UPDATE 되는 등 데이터 성격이 다름.
	* **Lock 경합:** 단일 테이블 관리 시, 조회수 증가를 위한 잦은 UPDATE로 인해 Row Lock이 발생하고, 이로 인해 단순 상품 조회 트랜잭션까지 대기해야 하는 성능 병목 즉, 동시성 저하 우려.
	* **구조적 모호함:** 통계 데이터가 상품 상세(DTL)에 종속될 지, 마스터(MAST)에 종속될 지 관계 설정의 명확성이 필요.
* **해결:** 
	* **수직 분할 적용:** 정적인 TB_PROD_MAST와 동적인 TB_PROD_STAT로 테이블을 물리적으로 분리한다.
	* **Star Schema 구조:** TB_PROD_MAST를 중심으로 상세(DTL), 통계(STAT), 이미지(IMG) 등이 식별 관계(1:1)로 연결되도록 설계하여 관계의 유연성 확보.
	* **결과** : 
		**성능 최적화:** 조회 트랜잭션과 갱신 트랜잭션을 분리하여 DB Lock 경합을 최소화하고 동시 처리 성능을 극대화함.
		**유지보수성:** 각 테이블의 역할이 명확해져 쿼리 복잡도가 낮아지고 확장성이 향상됨.

### 데이터 정합성 보장을 위한 NULL 처리 원칙 수립

* **배경:** 이커머스 시스템은 금액 연산, 주문 상태 변경 등 데이터의 정확성이 핵심이나, 무분별한 NULL 허용 시 연산 오류(SQL 집계 왜곡) 및 런타임 예외(NPE) 발생 위험이 큼.
* **문제:** 
	*  Java 어플리케이션에서 값을 꺼낼 때마다 NullPointerException 방지를 위한 방어 로직 (if != null)이 과하게 늘어나는 문제.
	* 특히 협업을 고려할 시, NULL 허용 여부에 대한 명확한 기준이 없으면 개발자 간 설계 스타일이 다르므로 NPE에 관한 문제가 더 커질 수 있음.
* **해결:** 
	* **존재 가치 판별:** 행(Row)의 식별에 필수적인 데이터(주문자, 결제수단 등)는 무조건 NOT NULL로 강제하여 데이터 무결성 확보
	* **상태/필수 값:** 주문 상태나 결제 수단은 필수 정보이므로, 데이터 입력 시 반드시 유효한 값을 넣도록 강제.
	* *연산 안정성 판별:* 금액(PRICE), 수량(QTY) 등 사칙연산 대상은 NULL 대신 Default 0을 부여하여 SQL 집계 오류 및 NPE 원천 차단.
	* **미래 시점 값:** START 시점은 알 수 있지만, END 시점은 알 수 없으므로 예외적으로 NULL 허용.

* **결과** : 
	* **시스템 안전성:** SQL 통계 쿼리의 정확성을 보장하고, DB 레벨에서 잘못된 데이터 유입 차단함.
	* **코드 간결화:** 불필요한 Null 체크 코드를 제거하여 로직을 간결하게 만들고, 널 포인트 예외(NPE) 발생 가능성을 제거함.


### 다양한 DBMS를 고려한 스키마 표준화

* **배경**: 특정 DB(MySQL 등)에 종속적인 데이터 타입(TINYINT, Boolean 등) 사용 시 추후 마이그레이션이나 솔루션 확장 시 호환성 우려.
* **해결:** 
	* **Boolean 대체:** CHAR(1) ('Y', 'N')를 사용하여 Oracle 등 다른 DBMS와의 호환성 확보 및 가독성 증대함.
	* **TIME 타입:** TIMESTAMP는 2038년까지만 지원되므로, 대신 DATETIME을 채택하여 안정성 확보.
	* **대문자:** 고객사가 Oracle을 사용할 가능성을 열어두고 네이밍은 대문자로 지정.
	* **공통 컬럼 규칙:** 모든 테이블에 생성, 수정, 삭제 정보 (CDT, UDT, DDT)를 필수적으로 포함하여 데이터 추적성을 확보함. (감사 등 대비)


### I/O 성능 최적화를 위한 DB 수직 분할
* **배경:** 쇼핑몰 트래픽 특성상 상세 페이지 조회보다 상품 목록(List) 트래픽이 압도적으로 많음.
* **문제:**
	* 상품 상세 설명(TEXT/LOB)처럼 대용량 컬럼을 마스터 테이블에 함께 보관 시, 데이터 행의 크기가 지나치게 커져서 데이터베이스 성능에 부담을 줌.
	* DB는 Page 단위 I/O를 수행하는데, Row가 크면 한 페이지에 담기는 레코드 수가 줄어드는 문제.
	* 결과적으로 목록 조회 시 불필요한 입출력이 증가하고, 메모리에 불필요한 데이터가 적재되어 캐시 적중률이 저하됨.
* **해결:**
	* **테이블 수직 분할:** 자주 조회되는 경량 데이터(상품명, 가격)는 TR_PROD_MAST에, 무거운 LOB 데이터(상세설명)는 TB_PROD_DT로 분리하여 1:1로 설계.
	* **조회 전략 차별화:** 트래픽이 많은 목록 조회 시에는 가벼운 MAST 테이블만 스캔하여 부하를 최소화.
* **결과:**
	 * **입출력 효율 극대화:** 한 페이지 당 더 많은 정보를 조회할 수 있또록 데이터를 높여, 목록 조회 속도를 물리적으로 단축.
	 * **메모리 효율화:** 자주 조회되는 핵심 데이터 위주로 DB메모리(Buffer Pool)를 점유하게 하여, 불필요한 캐시 낭비를 막고 전체적인 처리 성능을 높임.


### 데이터 성격에 따른 파일 관리 테이블 이원화
* **배경:** 시스템 내에서 발생하는 다양한 파일들(배너, 상품 이미지 등)을 저장하는 방식 설계
* **문제:** 
	* 배너, 팝업, 게시판 등 시스템 전체적으로 다양하게 사용하는 파일들과 달리 상품의 일부로서 sortby나 상품 번호에 따라 세부적으로 관리해야 할 필요성이 있었음.
* **해결:** 
	* 테이블을 이원화하여 TB_PROD_IMG에 상품 이미지를 따로 관리하고 나머지는 TB_FILE_MAST에서 관리 하도록 함.
* **결과:** 단순 파일은 쉽고 편하게 관리하고, 중요한 상품 이미지는 기능에 맞춰 엄격하게 관리하여 운영 효율성을 높임.


### 운영 안정성을 위한 생명주기 및 Soft Delete 설계 표준화

* **배경:** 애플리케이션 내 데이터에 대해서 등록, 수정, 삭제 등 데이터의 생명주기를 관리하는 로직 설계
* **문제:**
	* 단순 물리적 삭제(DELETE) 시, 관리자의 조작 실수로 인한 데이터 영구 소실 위험 존재.
	* 삭제된 데이터의 이력을 추적할 수 없어 운영 히스토리 파악 또는 감사가 어려움.
* **해결:** 
	* **Soft Delete(논리적 삭제) 도입:** 데이터를 DB에서 실제로 지우지 않고, 삭제 일시 DDT의 업데이트를 통해 보존하는 방식 채택.
	* **상태 이원화:** 파일에 따라 ACTIVE, PENDING, ARCHIVE ... 등 역할을 명확히 분리 설계.
* **결과:**
	* 실수로 삭제된 데이터의 즉시 복구가 가능해져 운전 안정성을 확보하고, 과거 데이터에 대한 추적성을 유지함.

### TB_File_MASTER의 DOMAIN_NO를 통한 분류

* **배경:** 배너, 게시판, 팝업 등 시스템 전반의 다양한 도메인에서 공통적으로 파일(이미지 등) 첨부 기능이 요구 됨.
* **문제:**
	*  도메인마다 파일 테이블을 따로 만들면 관리가 비효율적임.
	* 반대로 하나로 통합할 경우, 이 파일이 어떤 테이블의 몇 번째 게시물에 속하는지 식별하기 어렵고, 특정 용도(예:PC용 배너)의 파일이 중복 등록되는 것을 막기 어려움.
* **해결:** 
	* **다형성 컬럼 도입:** DOMAIN_TYPE(대상 테이블), DOMAIN_ID(대상 PK), FILE_PURPOSE(용도) 3가지 컬럼을 통해 어떤 도메인의 데이터와도 연결될 수 있게 설계.
	* **복합 유니크 제약:** 위 3개 칼럼(TYPE + ID + PURPOSE)을 묶어 UNIQUE키를 설정.
* **결과:**
	* **유연성:** 단일 테이블로 모든 도메인의 파일 관계를 유연하게 처리(JOIN) 가능.
	* **무결성:** 하나의 대상(ID)에 대해 동일한 용도의 파일이 중복 등록되는 사고를 DB레벨에서 원천 차단함.


## 단일 책임 원칙에 기반한 파일 서비스를 계층화
* **배경:** 상품, 리뷰, 공지사항 등 다양한 도메인에서 파일 업로드/다운로드 기능을 공통으로 사용해야 함.
* **문제:** 
	* **God Class 위험:** 하나의 FileService에 모든 도메인의 비즈니스 로직(상품 권한 체크, 리뷰 작성자 확인 등)을 집중시킬 경우, 클래스가 비대해지고 메소드 폭발 현상 발생.
	* **높은 결합도:** 단순한 파일 I/O 로직과 도메인별 비즈니스 규칙이 뒤섞여, 특정 도메인의 정책 변경이 공통 파일 서비스 코드 수정으로 이어지는 강한 결합 발생.
* **해결:** 서비스 계층화 전략 적용.
	* **Infrastructure Layer(FileService):** 도메인별 Service에서 해당 도메인별 파일에 관한 경로를 조립(ex : /app/product/도메인/년/월/일/파일)
	* **Domain Layer (ProductFileService) ::** 해당 도메인의 비즈니스 규칙(유저 권한 검증, 다운로드 횟수 차감 등)을 수행 후, FileService를 호출하도록 위임.
* **결과:**
	* **높은 응집도:** 도메인별 규칙이 각 서비스(ProductFileService, ReviewFileService 등)에 집중되어 관리 용이.
	* **유연한 확장성:** 새로운 도메인이 추가되었더라도 기존 FileService 코드를 전혀 수정할 필요 없이 확장 가능.

### 유지보수성을 위한 DTO 계층화 및 클래스 폭발 방지 전략
* **배경:**  화면이나 로직마다 요구하는 데이터 필드가 미세하게 달라(예: 가격만 조회, 이미지만 조회 등), 이를 위해 매번 별도의 DTO파일을 생성해야 하는 상황.
* **문제:**
	* 모든 DTO를 개별 파일로 생성 시, 프로젝트 내 파일 개수가 기하급수적으로 늘어나는 클래스 폭발 현상 발생.
	* IDE 탐색이 어려워지고, 도메인 로직과 관련된 DTO들이 여기저기 흩어져 응집도가 저하됨.
* **해결:** DTO의 사용 범위와 목적에 따라 관리 방식을 이원화하는 하이브리드 전략 채택.
	* **전역 DTO (Global):** 테이블과 1:1로 매핑되거나 프로젝트 전역에서 재사용되는 핵심 DTO는 개별 파일로 관리하여 재사용성 확보.
	* **지역 DTO (Local):** 특정 도메인 내에서만 쓰이는 소규모 데이터는 도메인별 CommonCto 내부의 Static Inner Class로 정의하여 관리.
* **결과:**
	* 불필요한 파일 생성을 억제하여 프로젝트 구조를 깔끔하게 유지.
	* 관련된 소규모 DTO들을 한 곳에 모아둠으로서 도메인 응집도를 높이고 유지보수 효율을 개선함.

### 비즈니스 확장성을 고려한 범용 재고 처리 로직 설계

* **배경:** 디지털 상품 위주의 이커머스로서 기획했지만, 향후 실물 상품 배송 판매로의 비즈니스 확장 가능성이 존재함.
* **문제:**
	* 디지털 상품(주로 상품 1개 제한)에 맞춰 로직을 하드코딩할 경우, 추후 실물 상품(대량 주문, 합배송) 도입 시 재고 처리 코드를 전면 재작성 해야 하는 기술적 부채 발생.
* **해결:**
	* **로직의 범용화:** 재고 차감 로직을 처음부터 대량 처리가 가능한 구조로 설계
	* 제약 조건 분리: 디지털 상품의 '1회 1개 구매 제한'은 핵심 로직을 수정하는 것이 아니라, 상위 레이어에서 상품 타입(PRODUCT_TYPE)에 따른 정책(policy)으로 제어하도록 설계.
* **결과:**
	* 비즈니스 모델이 실물 상품으로 확장되더라도 핵심 코어 로직 수정 없이 유연하게 대응 가능한 아키텍처 확보.
	* 다양한 시나리오에 대한 단위 테스트를 통해 로직의 견고함을 미리 검증함.

### 대용량 트래픽을 고려한 파일 디렉토리 구조 최적화
* **배경:** 상품 리뷰, 문의 내역 등 지속적으로 늘어나는 업로드 파일의 서버 내 저장 경로를 설계함.
* **문제:**
	* **초기 설계:** /도메인/ID/파일 (ex: /product/101.a.jpg)의 단순 구조.
	* **성능 리스크:** 특정 상품이 '베스트셀러'가 되어 수만 건의 리뷰가 달릴 경우, 단일 디렉토리 내 파일 개수가 과도하게 증가.
	* **관리 및 추적의 어려움** 트래픽이 많은 쇼핑몰 특성상 파일이 빨리 쌓이므로, 단일 경로 내 파일들을 모아두면 향후 오래된 데이터나 오류 추적 등 유지보수가 어려움.
	* **OS 제약 :** 리눅스 파일 시스템 특성상 한 디렉토리에 파일이 과도하게 적재되면 입출력 병목 현상 발생.
* **해결:** 날짜 기반의 계층적 디렉토리 구조 도입.
	* **변경 설계:** /도메인/ID/년/월/일/파일 (ex. /product/2025/12/11/a.jpg)
	* 파일을 생성 일자별 서브 디렉토리로 분산 저장하여 폴더 당 파일 개수를 적절히 통제
* **결과:** 
	* **I/O 성능 보장:** 데이터 양과 무관하게 일정한 디렉토리 탐색 속도를 유지.
	* **운영 효율성:** 날짜별로 폴더가 정렬되어 있어, 로그 추적이나 백업 및 기간별 데이터 관리가 수월해짐.

### 파일 정책별 저장 상태 
* **배경:** 파일 업데이트 시 기존 파일을 처리하는 방식에 대한 정책 수립이 필요했음.
* **문제:** 
	* 수정 전 파일들을 남겨두면 잘못된 수정에 대한 파일의 복구는 용이하지만 대용량의 스토리지를 소모하게 되는 문제 발생.
	* 무조건 덮어쓰기를 할 경우, 필요 시 중요 파일의 복구가 불가능한 문제가 발생함.
* **해결:**
	* **단순 리소스 (상품 이미지, 배너 등)** : 최신 상태가 중요한 파일들은 Overwite 정책을 통해 삭제, 스토리지 낭비 방지.
	* **중요 리소스 (계약서, 증빙서류 등)** : 법적 이슈 및 히스토리 파악이 중요하므로 이전 파일을 ARCHIVED 상태로 변경(soft delete)하고, 파일 데이터 새로운 행 추가.
* **결과:**
	* 스토리지 관리 효율성 및 데이터의 복구 가능성 사이의 균형을 맞춘 합리적 시스템 구축.

### 배포 환경 변화에 유연한 파일 경로 관리

* **배경:** 서버에 파일을 저장할 file 경로 지정하는 방식에 대해 고민. Java 코드 내 static final로 선언할 지, application.properties에 할 지 고민.
* **문제:**
	* **java 코드 내 할 경우:** 개발 환경(Windows)와 배포 환경(Linux)의 경로 (C:\ , home/)가 달라 질 때 마다 코드를 수정하고 재배포해야 하는 유연성 및 유지보수성 문제 발생.
	* **관심사 분리 문제:** Java에 코딩할 경우 배포 환경 설정은 application.properties에 설정한다는 관심사 분리 문제에 위배 됨.
* **해결:** Spring Boot의 application.properties 및 @Value 어노테이션을 활용한 외부 설정 파일 관리 방식을 채택.
	* 경로 변경이 필요할 경우, 코드 수정 없이 외부 설정 파일만 변경 후 서버를 재시작하는 유연성 확보.
* **결과:** 
	* **환경 독립성 확보:** 개발과 배포 환경에 구애받지 않고 유연하게 경로를 변경할 수 있는 구조를 구축.
	* **유지보수 효율 증대:** 사소한 설정 변경에도 전체 프로젝트 컴파일 및 배포가 불필요해짐.
	

### 지원 종료된 Tiles 대체 및 레이아웃 관리 효율화
* **배경:** 웹 페이지의 Header, Footer 등 공통 레이아웃을 일관성 있게 관리해야 했음. 일반적으로 많이 사용되는 Tiles를 사용 검토함.
* **문제:** 
	* **중복 코드 발생:** 타일즈를 쓰지 않으려니, 모든 컨트롤러에서 '현재 메뉴 활성화' 등을 위해 curUrl(현재 URL) 정보를 뷰로 넘겨줘야 하는 반복 작업이 발생.
	*  **기술적 부채:** Tiles는 지원이 중단 된 라이브러리로서, Spring Boot 철학(XML)과 맞지 않으며 설정 복잡도가 높음.
* **해결:** Native JSP Include 및 Interceptor를 활용한 역할 분담.
	* **Interceptor 활용:** LayoutInterceptor를 도입하여, curUrl과 같은 UI 제어용 공통 속성을 postHandle 시점에 일괄 주입. 개별 컨트롤러의 간섭 없이 '현재 메뉴 하이라이팅' 기능을 구현. 
	* **클라이언트 로직 분리:** 로그아웃 시 CSRF 토큰 처리나 입력값 유효성 검증(Enum 활용) 등 즉각적인 반응이 필요한 로직은 Modern JS(ES6+)로 위임하여 서버 부하를 줄임.
	* **결과:**
		* **유지보수성:** XML 설정 없이 JSP 파일만으로 레이아웃을 구성하여 직관성을 높임.
		* **코드 중복 제거:** 컨트롤러는 비즈니스 로직에만 집중하고, 뷰 렌더링을 위한 부가 정보는 인터셉터가 자동으로 처리하는 깔끔한 구조 확보.
