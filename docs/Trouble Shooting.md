* **문제 상황:** `Safelist` 클래스 자체에 커스텀 필터링 메소드를 추가하여 `XssReadableRequestWrapper` 에서 사용하고자 했으나, `Jsoup` 과 같은 외부 라이브러리의 클래스를 직접 수정하는 것은 유지보수 및 확장성(OCP 원칙) 측면에서 지양해야 함을 인지함.
* **해결 방안:** 외부 라이브러리 코드를 수정하는 대신, Spring의 **의존성 주입(DI)** 을 활용하는 방식으로 설계를 변경함.
	1.  `WebConfig`에 커스텀 설정을 담은 `Safelist`를 `@Bean`으로 등록하여 관리하도록 함.
	2. `XSSFilter` **생성 시** 해당 `Safelist`빈을 주입받아 필터 내부 멤버 변수로 저장하고 사용하도록 구조를 개선함.
* **결과:** 라이브러리 원본을 훼손하지 않으면서도 프로젝트 상황에 맞는 유연한 필터링 정책을 적용할 수 있게 되었으며, 설정 변경 시 코드를 수정할 필요 없이 Bean 설정만 변경하면 되는 유연한 구조를 확보함.

### DDD 기반에 충실한 로직으로서의 리팩토링


* **문제 인식:**
    *  엔티티 사용 취지 이해 : 흔한 관습대로 서비스 계층에 비즈니스 로직을 주로 사용했으나, 견고한 DDD 설계를 위해서는 비즈니스 로직을 처리하는 엔티티에서 세부 로직의 처리를, 그리고 서비스 계층에서는 비즈니스의 전체 흐름 및 트랜잭션, 메일 발송 등의 이벤트 처리에 중점을 둬야 한다는 것을 깨달음.
    * DB 설계 : 전체적인 DB 스키마의 설계의 컨텍스트간의 경계가 명확하지 않음. 구매자, 판매자 등 컨텍스트 따로 명확히 구분하되, 기존 방식처럼 성능 면에서 타협을 보는 방식을 적절히 MIX할 방법으로서 리팩토링 필요. (도메인 주도 설계)
- **원인 분석 및 전략 수립:**
    
    - **빈약한 도메인 모델(Anemic Domain Model)의 한계:** 서비스 레이어가 모든 비즈니스 규칙을 소유하면서 엔티티가 단순한 데이터 바구니 역할에 그치고, 결과적으로 코드가 절차지향적으로 흘러 유지보수가 어려워지는 구조적 문제를 인지함 .
        
    - **관심사의 혼재와 도메인 경계 모호성:** DB 설계 시 성능 최적화를 위한 반정규화와 도메인 간의 논리적 격리가 충돌하면서, 특정 도메인의 변경이 시스템 전체에 영향을 주는 리스크를 확인하고 **바운디드 컨텍스트(Bounded Context)**를 명확히 정의할 필요성을 느낌 .
        
    - **실용적 하이브리드 전략:** 이론적인 DDD의 격리 모델을 지향하되, 이커머스의 특성인 '조회 성능'을 확보하기 위해 **수직 분할(Vertical Partitioning)**과 같은 물리적 최적화 기법을 전략적으로 혼합하기로 결정함 .
        
- **개선 및 리팩토링 계획:**
    
    - **Rich Domain Model로의 전환:** 재고 부족 여부 검증이나 상태 변경 유효성 체크 등 도메인 고유의 제약 조건은 엔티티 내부 메서드(Domain Logic)로 이관하여 캡슐화 수행.
        
    - **서비스 레이어 역할 재정의:** 서비스는 도메인 객체 간의 협력을 조율(Orchestration)하고, 트랜잭션 경계 설정 및 외부 시스템 연동(메일, 알림 등)과 같은 **흐름 제어**에만 집중하도록 리팩토링.

### 인터셉터를 통한 현재 메뉴의 url 경로 전달 방식(LayoutInterceptor)

* **문제 인식:**
    - **강한 결합도와 중복:** 초기에는 `AbstractBaseController`를 상속받아 레이아웃 데이터를 처리했으나, 이는 모든 컨트롤러가 특정 클래스에 의존하게 만들어 확장성을 저해하는 구조적 제약을 발견했다.
    - **설정의 복잡성:** 단순한 자체 정의 클래스임에도 불구하고 `@Configuration`에서 빈(Bean)으로 등록하여 관리하려다 보니, 불필요한 설정 코드가 늘어나고 관리 포인트가 분산되는 비효율을 확인하였다.
 * **원인 분석 및 전략 수립:**
    * **관심사 분리 (Soc) 실패:** 화면 레이아웃에 필요한 데이터(현재 메뉴 경로 등)는 비즈니스 로직과 별개인 '횡단 관심사'임에도 불구하고 컨트롤러 계층에 섞여 있었다.
    * **컴포넌트 스캔 활용:** 외부 라이브러리가 아닌 직접 구현한 클래스이므로, 스프링의 @Component 스캔 기능을 활용해 의존성을 스스로 관리하게 함으로서 설정 클래스와의 결합도를 낮추는 전략을 수립.
    * **유연한 UI 대응:** 현재 요청 URL을 인터셉터에서 가로채 HttpsServletRequest나 ModelAndView에 주입함으로써, 헤더(Header)나 사이드바(Sidebar)의 활성화된 메뉴를 동적으로 표시할 수 있는 기반을 마련.
* **개선 및 리팩토링 계획:** 
	 * **Intercetpor 기반 전환:** AbstractBaseController를 제거하고, HandlerInterceptor를 구현한 LayoutInterceptor를 도입하여 레이아웃 관련 로직을 단일 지점으로 응집.
	  * **@Component 기반 빈 등록:** 별도의 @Configuration 설정 없이 @Component 어노테이션을 통해 인터셉터를 자동 등록하고, WebMvcConfigurer에서는 해당 인터셉터의 적용 경로(Path Pattern)만 지정하여 설정을 최소화.
	  * **표준화된 경로 전달:** 모든 요청에 대해 현재 URL 정보를 공통 속성으로 전달함으로써, JSP 레이아웃 모듈화(jsp::include 등) 시 별도의 파라미터 전달 없이도 일관된 UI 상태를 유지하도록 리팩토링할 예정.


### 주문 번호 생성에서의 비관적 Lock 사용 문제 

* **문제 인식 : 
  * **병목 현상(Bottleneck):** 주문 번호 채번을 위해 DB 테이블에 명시적인 비관적 락을 걸 경우, 대규모 트래픽 발생 시 트레드 대기 시간이 길어져 시스템 전체의 처리량(Throughput)이 급감하는 구조적 한계를 확인.
  * **데이터 타입 부조화:** 기존의 `VARCHAR` 기반 주문 번호 (예: ORD20250122-0158)를 PK로 직접 사용할 경우, 인덱스 크기가 커지고 JOIN 성능이 저하되는 기술 부채를 인지.
* **원인 분석 및 전략 수립
  * **MES 레거시의 영향:** 생산 현장(MES)에서는 추적성(Traceability)를 위해 'ORD-날짜-시퀀스' 형태의 식별 번호가 필수적이었으나, 고성능 웹 서비스에서는 이를 PK로 유지하는 것이 성능 상 불리하다는 결론.
  * **원자적 검증의 필요성:** 재고 차감 시에는 원자적 업데이트(Atomic Update)를 통해서 락 없이 동시성을 제어했듯이, 주문 번호 생성 역시 DB 의존성을 낮추는 방향성을 모색 필요함을 느낌.
* **개선 및 리펙토링 계획
   *  **내부 PK와 보이는 ID의 분리:**
    * **Internal PK:** 실질적 데이터 매핑은 FK로서 `BIGINT AUTO_INCREMENT` 타입을 사용해서 DB 인덱스 성능 극대화.
    * **Visible Order No:** 사용자가 식별하는 주문 번호는 별도의 유니크 인덱스를 가진 컬럼으로 분리하여 비즈니스 식별성을 유지.
    * **REDIS를 활용한 고가속 채번 (Next Step):**
    * **Redis INCR:** DB락 대신 메모리 기반의 Redis INCR 명령어를 활용하여 원자성을 보장하면서도 초당 수만 건의 채번이 가능하도록 고도화 할 예정.
    * **분산 ID 고려:** 향후 프로젝트 확장 시 DB 성능과 안전성을 고려, Snowflake ID와 같은 DB를 거치지 않고 ID를 생성하는 분산 환경용 ID 체계를 검토.
    * **단계별 리펙토링:** `AUTO_INCREMENT` -> Redis -> 분산 ID
